## 修正内容

- `owner_booking_events` と予約INSERT時のトリガーで、予約と同じDBトランザクションに小さな通知イベントを保存。通信は予約処理から分離したワーカーで行う。失敗しても予約や決済の状態を書き換えない。
- 改修後のWEB・英語・電話・直接・VIP/LINE・Square・取込を同じ経路で拾う。既存予約の一括再通知はしない。旧仕様で承認された10月20日以降のWEB分だけ補完する。
- 明示された決済テストは通知対象外。テストは本予約とは別の一時DBで検証する。
- 一意な予約IDマーカーを保持。銀行振込の受付通知、朝倉個人トークの登録成功通知が既にあれば、同じoutboxと本文を引き継ぎ、追加の新規通知を送らない。
- 他のコンシェルジュ待ち行列が停止していても新規予約通知を先に処理。VIP向け配信停止は予約通知を取り消さない。
- 最大8回の自動試行、最初の試行から23時間の期限。月間上限は保留し同じ業務チャネルへの新規予約pushを止める。頻度制限は間隔を延ばす。内容不明の429、認証不備は盲目的に再送しない。
- DBで送信処理を確保し、多重起動を防止。通信前に試行履歴を保存。中断後は同じUUID・送信先・本文を使用する。送信先または接続トークンが変わった場合も保留する。
- HTTP 200、または受付ID付き409だけを`accepted`にする。受付時刻・request ID・accepted request ID・各試行結果を保存。
- 旧処理で試行済みの未完了予約通知は`legacy_history`で保留し、履歴照合を要求。既存の受付済み通知は再送しない。
- 認証付き `/api/reservation-notifications` と予約管理画面で保留・失敗・待機・API受付済み・試行履歴・代替通知状態を確認できる。端末への到達や既読とは区別する。
- 代替メールは通知ID単位で1回。SMTP受付結果が不明なら自動再送せず要確認にする。メールにお客様の連絡先や氏名は含めない。

## 設定

既存の `LINE_CHANNEL_ACCESS_TOKEN` と `concierge_settings.owner` を使用する。別チャネルやグループには切り替えない。

代替経路は `OWNER_NOTIFICATION_EMAIL` に確認済みの朝倉メールアドレスを設定し、既存の `SMTP_HOST`、`SMTP_PORT`、`SMTP_USER`、`SMTP_PASS`、`MAIL_FROM` を利用する。未設定なら管理画面で「未設定」。メールアドレスの推測や自動登録はしない。

## 本番復旧の順序

1. Renderでサービス、リポジトリ、デプロイブランチ、稼働コミット、永続ディスクを確認。19:50–20:10 JSTのログを保存し、HTTP 429本文、request ID、送信時刻を照合。
2. DBをSQLite backup APIでバックアップ。予約データを削除・変更しない。
3. 変更前のDBを読み取り専用で確認：

   ```bash
   python scripts/owner_notice_recovery.py --reservation-id 29
   python scripts/owner_notice_recovery.py --quota
   ```

   `--resume`なしの照合はDBをread-onlyで開き、通知本文・送信先ID・資格情報を出力しない。旧コードが保存していない情報は復元できない。`quota`は業務LINEの配信枠と使用量をGETするだけで送信しない。

4. LINE接続先を `/api/concierge/diagnostics` と本人連携情報で確認。月間上限なら契約・追加配信上限の対応後に配信枠を再確認。頻度制限なら他の送信処理も確認する。
5. 稼働ブランチと差分を照合してこの修正をデプロイ。ヘルスチェックと管理画面を確認する。旧再送ワーカーが残っていないことを確認。
6. #29のoutbox状態、既存メッセージID、全送信ログを照合する。受付済み・受付不明なら新しい通知を作らない。
7. 再開は記録された根拠付きで実行する：

   ```bash
   python scripts/owner_notice_recovery.py --reservation-id 29 --resume \
     --evidence '照合したログの日時・受付ID・判断根拠'
   ```

   旧履歴または期限超過の場合、すべての過去の送信が未受付と確認できた時だけ `--confirmed-not-accepted` を追加する。不明な履歴をこのフラグで代用しない。過去に受付済みまたはLINEメッセージIDがある通知は再開不可。自動回数上限に達している時の明示的再開は、履歴を保持して1回だけ追加の試行を認める。

   月間枠の確認成功後、まだ一度も試行していない保留分だけも再開する。その他の試行済み保留分は個別に照合する。
8. API受付記録を読み取り専用で再確認。朝倉のLINE画面の到達確認は別途実施し、「API受付済み」と「端末到達確認済み」を分けて報告する。
9. 本番の新規予約通知試験は、空席・支払・顧客通知への影響を確認してから、明示した架空名・連絡先なしの試験予約で実施。発行したテストIDだけを記録し、終了後に整理する。本予約 #29 は整理対象外。
