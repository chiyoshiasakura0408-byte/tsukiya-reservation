# 予約フォームのパスキー

## 対象と有効化条件

`/book` と `/book?lang=en` に予約用パスキーの案内を表示する。通常予約は引き続き手入力で完了できる。パスキー登録は予約後に任意で実施する。対象は、確定したWeb予約の氏名・メール・電話が紐付け済みの顧客レコードと一致する予約。予約番号と両方の連絡先が一致した場合に限り、別々の確認コードをメールとSMSに送る。

有効化には以下が必要。

- `APP_BASE_URL` を予約フォームを公開する正規のHTTPSオリジンに設定する。パスキーはこのホストに紐づく。
- `GUEST_PASSKEY_SECRET` に他の用途と分離した32文字以上のランダムな値を設定する。値はログやリポジトリに書かない。変更すると以前の本人確認情報での呼び出しが無効になるため、計画的に扱う。
- 既存SMTPとSMSが利用可能であることを確認する。`GUEST_PASSKEY_ENABLED=1` は受入テストを終えた環境で設定する。初期状態は無効。

## 保存と権限

- SQLiteに顧客ID・本人確認に使った予約ID・ランダムなユーザーハンドル・本人確認情報のHMAC、公開鍵、署名カウンターを追加する。顔画像、指紋、端末PIN、秘密鍵、カード情報は保存しない。
- 認証結果は成功した同じ画面へ一度だけ返す。継続ログイン用のCookieは発行しない。認証チケットはサーバー側で期限を設け、使い切りとする。
- お客様に返すのは氏名、電話、メール、領収書宛名だけ。予約・顧客の紐付けや本人確認情報が変わった場合は呼び出しを拒否する。領収書宛名は新規予約単位でも保存でき、既存の顧客台帳を自動で上書きしない。
- 登録可能なパスキーは顧客ごとに1件。機種変更時はメールとSMSを使って再登録できる。新しい登録に成功した時点で以前の鍵が無効になる。認証済みの利用者は案内画面から解除できる。両方の連絡先を使えない場合は、店舗が別途本人確認して訂正するまで手入力で予約できる。
- パスキーの解除は予約履歴や顧客台帳を削除しない。顧客情報の訂正・削除の依頼は、店舗の既存の窓口で扱う。

## リリースと切り戻し

1. 本番とは独立したSQLite、SMTP、SMS、Square Sandboxを用意する。実機のiPhone・Android・PCで登録、呼び出し、キャンセル、機種変更時の再登録を検証する。初回予約、決済拒否後の再試行、支払い確定と通知の連携も確認する。
2. 現行のスタッフ用認証と管理APIのアクセス経路を確認し、管理者MFAの導入・運用確認を完了する。この変更はスタッフ認証を変更しない。
3. 永続ディスクのバックアップを取得する。SQLiteのオンラインバックアップ機能などで整合したコピーを取り、アクセスを制限した保管先で `PRAGMA integrity_check` と復元手順を確認する。
4. 新しいコードを機能無効のままデプロイし、日英の予約ページと決済導線を確認する。次に機能を有効化し、合成テスト用の予約だけで動作を確認する。
5. 不具合時は `GUEST_PASSKEY_ENABLED=0` に戻す。必要なら直前のアプリ版に戻す。追加列・テーブルはそのままで動作し、機能の停止にDB復元は不要。古いバックアップで現在の本番DBを上書きすると、公開後の予約・決済を失うため避ける。
