# つきや予約管理 GPT Actions API

管理者が `/gpt-setup` で初回設定し、自分のみの専用GPTへOpenAPIをインポートする。
スキーマURL: `https://tsukiya-reservation.onrender.com/api/gpt/openapi.json`
認証: API Key / Bearer。`GPT_RESERVATION_API_KEY` に40文字以上のランダム値を設定する。
OpenAIのAPIキーではなく、この予約API専用の秘密鍵。キー未設定時は全データ操作を拒否する。
管理者向けキー取得は既存のスタッフ認証と同一オリジンPOSTが必要。
通常のチャットには自動接続されない。専用GPT側のアクション設定と保存が必要。

対応: 接続状態、日付範囲検索（32日以内、100件ずつ）、詳細、空席確認、
直接予約／電話予約、備考、時刻、人数、個室変更。
日時はAsia/Tokyo。新規受付は18:00／20:30。料金・席数・休業日等は既存のサーバールールを使う。
電話予約では既存仕様に従ってSquare請求・通知が発生し、直接予約でもメール指定時には確定通知が発生する。
時刻／人数／個室の変更は既存の直接予約用制約に従う。備考変更は現在の備考を照合する。
GPTキーは既存の管理APIには通用しない。取消、返金、入金確認、顧客編集は公開しない。

書き込みには小文字UUIDの `request_id` が必要。同一内容の再試行は保存済みの応答を返す。
異なる操作への再利用と、処理途中でプロセスが停止して結果不明の場合は409で拒否する。
その際は予約一覧と管理履歴で事実を確認し、新しいIDで盲目的に再登録しない。
予約処理・外部送信と応答記録は単一の分散トランザクションではない。
ログはSQLiteの `gpt_api_requests` と `gpt_api_audit`。キーやリクエスト本文をアクセスログに書かない。
キーの失効・交換はRenderの当該環境変数を変更して再デプロイし、専用GPTの認証設定も更新する。

検証: `python -m unittest discover -s tests -p 'test_gpt_reservations.py'`
テストは隔離DBとSquare／通知のモックを使用。本番のテスト予約や請求は作成しない。
